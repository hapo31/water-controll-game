# シミュレーション中の速度調査

> この文書は256×256への拡張前の履歴です。現在の地形・計算方式・検証は [流域拡張の記録](basin-validation.md) と [水モデル](water-model.md) を参照してください。

実施日：2026-10-03。前半は約3 FPSの原因を調べた変更前の記録。後半に、依頼を受けて適用した最適化と再検証を記録する。前半の行番号・計測スクリプトは変更前の版を指す。

## 結論

主なボトルネックは `scripts/view/world_view.gd` の地形・水面描画。64×64セルの各面について `draw_colored_polygon()` を個別に呼び、シミュレーション更新のたびに描画命令を作り直している。

通常の全機能実行で **2.84 FPS / 352.24 ms毎フレーム**を再現した。水の計算を止めて描画だけを繰り返しても3.27 FPSだった。雨のパーティクルを外しても2.90 FPSで、主因を説明する改善はなかった。

## 条件と測定方法

- Windows、Godot 4.7.2 stable、Compatibility / OpenGL 3.3。
- CPU：AMD Ryzen 9 5900X、GPU：NVIDIA GeForce RTX 4070 Ti、ドライバー576.88。
- 画面1360×860、固定64×64マップ、豪雨。各ケース開始前に160刻み（シミュレーション8秒）進め、水がある状態を揃えた。
- 実際に描画する別プロセスを画面外に配置。検証側のみVSync無効・上限120 FPS。各ケース1.5秒以上の準備後、4秒以上測定。
- `Time.get_ticks_usec()` で関数・処理区間のCPU側経過時間を計測。FPSは描画終了フレーム数と実経過時間から算出。描画呼出数は `Performance.RENDER_TOTAL_DRAW_CALLS_IN_FRAME`。
- 一時的な派生スクリプトを `work/profiling/` に置いた。元の8スクリプトはSHA-256一致を確認した。水計算は元の `step()` を計測用に複写し、区間タイマーのみ追加。
- 短時間の比較計測であり、微小な差は誤差を含む。エディター内蔵実行や他の解像度で同じFPSになる保証はない。

## 処理を外した比較

| 条件 | 平均FPS | 平均フレーム時間 | 平均描画呼出数 |
|---|---:|---:|---:|
| 全機能 | 2.84 | 352.24 ms | 16,785 |
| 雨パーティクルのみ無効 | 2.90 | 344.95 ms | 16,784 |
| 地形・水面の描画命令を再生成せず、前の絵を維持 | 10.92 | 91.58 ms | 16,781 |
| 計算だけ継続し、地形・UI・雨を非表示 | 120.00（設定上限） | 8.33 ms | 0 |
| 水計算停止、地形・水面を毎フレーム再生成 | 3.27 | 306.18 ms | 16,755 |
| 水計算停止、描画命令も再生成せず、前の絵を維持 | 16.27 | 61.45 ms | 16,755 |

前の絵を維持するケースでも、保存済みの描画命令は毎フレーム描画される。そのため再生成の省略だけでは大量の描画呼出を解消できない。120 FPSの行は地形を表示しない比較実験であり、改善後のゲーム画面の速度を示すものではない。

|---|---:|---:|---|

水計算は12フレーム中32刻み実行されたため、1回と1フレームの値が異なる。メイン処理全体は平均37.40 msで、水計算・統計・カーソル更新を含む。上記に重ねて加算しない。

フレーム全体352.24 msからメイン処理37.40 msと `_draw()` 131.96 msを引いた約182.9 msは、この関数タイマーの外側にある。描画命令の管理・レンダラー・ドライバー・同期などの詳細内訳までは分離していない。これをGPU実行時間そのものとは扱わない。描画を省いた比較実験と大量の描画呼出から、描画経路全体が支配的と判断できる。

## 描画内部の追加計測

シミュレーションを止め、同じ水の状態で描画APIを個別に計測した。

- `draw_colored_polygon()` は**再描画1回につき16,335回**。その呼出内で合計**113.10 ms**、 `_draw()` 全体は136.20 ms。追加タイマーの負荷を含む別測定なので、上表と完全には一致しない。
- 座標・色・ポリゴンの計算は続け、ポリゴンの描画API呼出だけを省くと **54.94 FPS**、 `_draw()` は16.99 msになった。
- 水を描かず地形だけを毎フレーム生成しても、ポリゴン9,591個、**5.78 FPS**。水面だけを対象にしても十分な改善にはならない。
- `world_view.gd:98,101,102` が地形側面と上面、`:107,108` が水側面と上面の描画。`main.gd:156` の `_refresh()` が更新ごとに `queue_redraw()` を呼ぶ。

## 水計算内部の内訳

1刻み平均13.05 msのうち、隣接セル間の流量候補計算が5.49 ms、流量の適用が4.58 ms、蒸発・最大水深更新が1.37 ms、水量確定が0.97 ms。残りは降雨・供給量の制限・排水・バッファ初期化など。

隣接する辺は64×64で8,064本。候補計算と適用でそれぞれ走査する。計算側にも改善余地はあるが、描画を外すと20刻み/秒の進行を維持できており、今回の約3 FPSの第一原因ではない。

## 改善する場合の優先順位

1. **描画呼出をまとめる。** セルの各面を毎回個別に描く構成から、一定範囲ごとに頂点・色をまとめたメッシュなどへ移す。斜め見下ろしの重なり順と水の透明度を維持する必要がある。
2. **変更のない地形の再生成を減らす。** 地形変更時のみ必要範囲を更新し、水面の変化は対応する頂点・色を更新する。キャッシュだけでは描画呼出数の問題が残るため、1と組み合わせる。
3. **その後で水計算とセル探索を改善する。** 描画改善後に再計測し、隣接辺走査やカーソル探索の候補範囲を絞る。雨やFPS表示の削除を優先する根拠はない。

### 通常の表示設定での追加確認

プロジェクトの表示設定を変更せず、VSync有効・FPSの追加上限なしでも確認した。豪雨を60実験秒進めた状態から、画面外の同サイズウィンドウで6秒間測定：**165.10 FPS、平均6.06 ms、95パーセンタイル9.81 ms**。その6秒間に水理計算も6実験秒進行。水計算3.53 ms、描画更新1.64 ms、描画呼出82回だった。実際の表示FPSはモニターや実行環境に依存する。

### 正しさの検証

- 既存の水理・状態保持52項目：失敗0。
- 変更前との比較700刻み：天候変更と堤防の盛土・掘削を含め、全セルの水量・最大水深・流向、全辺の移動量、入出水台帳が毎刻み完全一致。
- 初期状態、豪雨、盛土・掘削後、水だけの初期化、フルリセット、深い水の6画像：変更前とのRGB差は1成分平均0.077〜0.089 / 255。20段階を超える色差の画素は0。メッシュの色量子化による微小差を許容し、重なり順・色・水面・矢印・ラベル・選択枠を比較した。
- 同6状態、合計1,500地点のセル探索：変更前と一致。セル中心・共有辺・画面外を含む。
- 盛土・掘削の長押し・ドラッグ24項目、FPS・ホバー・雨・カメラ11項目、天候・初期化16項目：失敗0。
